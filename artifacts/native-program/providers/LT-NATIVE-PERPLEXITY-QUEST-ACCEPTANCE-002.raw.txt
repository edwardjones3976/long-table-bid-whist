Using only current official public primary sources from Meta, Epic Games, Khronos, and Android, design a reproducible acceptance evidence protocol for a seated Meta Quest 3/3S application built with Unreal Engine 5.7.4. Focus on observable proof, not implementation advice. Cover: unchanged APK/AAB identity across tests; package signing, install, cold launch, relaunch, and log capture; controller and hand-tracking operation plus safe live modality switching; haptics and spatial-audio checks; mixed-reality passthrough/table placement/anchor recovery with a deliberate VR fallback; frame-time, thermal, memory, draw-call and battery evidence; accessibility/comfort checks suitable for adults ages 30-70; and two-headset tests that prove concealed card state is never exposed to the wrong player. For each test state the official source URL and title, supported observable signal, exact command/tool or device UI where officially documented, pass/fail evidence to retain, version/date limits, and any contradiction. Use at most 10 sources. Mark NOT ESTABLISHED whenever official sources do not define a method or threshold. Do not use private data, repositories, code, forums, blogs, social media, or third-party tutorials. Research only: no product verdict, legal conclusion, security certification, store approval, implementation decision, or external action.

Below is a research-only acceptance-evidence protocol, constrained to official public primary material from Meta, Epic Games, Khronos, and Android. It does not prescribe how to implement the application or assert store/security certification. Where the official sources do not provide a test procedure, measurement definition, or acceptance threshold, the protocol explicitly says NOT ESTABLISHED.

Scope and evidence rules

Test article: one designated release artifact for a seated Quest 3 / Quest 3S build made with Unreal Engine 5.7.4. Record the engine version as a declared test condition; the official Epic page located confirms Android requirements apply to UE 5.7 or newer, but it does not independently establish a Quest-specific UE 5.7.4 acceptance suite.
epicgames

Run controls for every test

Use two individually identified headsets: H1 and H2. Retain the headset model, serial or locally assigned device ID, Horizon OS build, battery percentage at start/end, controller firmware/state, test date/time/time zone, package name, and tester ID.

Assign a unique RunID, such as Q3S-H1-2026-08-31-R03, to every recorded execution.

Preserve original, unedited artifacts. Screenshots and videos should include the visible device clock or a separate synchronized time record where feasible.

Retain command text and raw terminal output, rather than only screenshots of “success.”

For each scenario, create a brief evidence index linking the test case, artifact hash, device, capture filenames, and verdict.

Keep source snapshots or access dates. The documentation cited below was available as of August 31, 2026; Meta and Android tooling, headset OS behavior, and Unreal point releases can change.

Acceptance convention: an item passes only when its documented observable signal is present, the retained evidence is complete, and no contradictory signal is found. Any requirement without a publicly documented official method or threshold is not silently inferred; it is marked NOT ESTABLISHED.

Interpretation boundaries

A successful apksigner verify demonstrates Android signature verification for the tested APK; it does not establish product security certification or identical installed AAB split composition.

A clean VrApi capture demonstrates observed runtime fields during that run. It does not establish a published Quest 3/3S frame-time, thermal, memory, or battery acceptance target. Meta’s cited documentation also makes clear that VrApi’s development API was deprecated, while its logcat tag remains available for OpenXR runtime statistics.
developers.meta

Meta’s compositor diagnostics can visibly and textually support claims about submitted compositor layers, their order, transforms, layer counts, and certain texture properties. They cannot by themselves prove a real-world table was semantically detected, that an anchor is durable, or that a visible object has a specified physical accuracy.
developers.meta

Android accessibility guidance supports manual testing, accessibility-service testing, analysis tools, and user testing. It does not create a Quest XR comfort standard, and TalkBack evidence should be claimed only for surfaces that actually participate in Android accessibility behavior.
developer.android

The two-headset protocol provides test-bounded observational evidence. The strongest accurate conclusion is: “No wrong-player concealment exposure was observed in the retained, predefined scenarios.” It cannot honestly establish “never exposed” across all code paths, future OS versions, network conditions, memory inspection, or untested sequences because no official source in the allowed set defines that proof standard.
