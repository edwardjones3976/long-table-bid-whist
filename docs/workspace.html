The workspace: one repository, many writers

The longer guide for AI coding agents (called providers on this page) that work on this game, and for the people who direct them. The short rules are in AGENTS.md. What the app is and how it is built is in mansion-app.html. If a command does something different from what this page says, trust what the command prints and tell the workspace owner.

1. What a lane is, and why

Many providers work on this game at the same time, each with its own tools. If they all wrote into one folder, one would overwrite another's files, a test would fail and nobody could tell whose change broke it, and nobody could say who wrote what. The answer here is simple: one repository, many writers, and nobody overwrites anybody. Every provider works in its own lane.

A lane is a second folder of the same repository, on its own branch (git calls this a worktree). With a lane you get four things:

You getWhat it is
A folder_provider_worktrees/<provider>-<task> inside the main folder. Git ignores that folder name and the main folder's test runner skips it, so your files never show up in anyone else's work.
A branchlane/<provider>-<task>. Your reviewed work is committed to it before it is merged into the game.
AreasThe folders and files you may edit. No other lane can claim them while you hold them.
Two portsOne for your game server and one for your client, so several lanes can run the app at the same time.

Words used on this page

WordMeaning
Main folderThe repository's first checkout, where the workspace owner works. Its ports are 3000 and 5173.

The lane's facts: .lane.json

Each lane keeps its facts in a small file at its top, .lane.json. Git ignores it. The main folder has one too once the workspace owner has claimed an area there: its provider is owner, its task is main, its number is 0 and its ports are 3000 and 5173. The lane commands write this file. Do not edit it by hand.

{
  "provider": "codex",
  "task": "tonk-bot",
  "number": 1,
  "serverPort": 3101,
  "clientPort": 5201,
  "areas": ["server/games/tonk-bot.ts", "tests/server/tonk.test.ts"],
  "base": "0123456789abcdef0123456789abcdef01234567",
  "created": "2026-11-18T17:20:05Z"
}

base is the commit the lane started from, and created is when it was made, in UTC. The values above are examples.

2. The lane commands

Every command is typed as npm run lane -- <command>. Keep the two dashes: without them npm keeps options such as --area for itself and the tool never sees them. The tool is one file, tools/lane.mjs, and needs nothing but Node, npm and git. It behaves the same from cmd, Git Bash and a POSIX shell, and it works when folder names contain spaces.

CommandRun it inWhat it does
new <provider> <task> --area <path> [--area <path> ...] [--install]The main folder, or any laneMakes a lane from the integration branch: the folder, the branch, the smallest free lane number (starting at 1) with its two ports, and .lane.json. With --install it also runs npm ci in the lane. It prints the lane folder, the ports and the next commands, and says plainly that work not yet committed in the main folder is not in the lane.
statusThe main folder, or any lanePrints one block for the main folder and one for each lane: provider, task, branch, areas, ports, how many files differ from its base (committed or not, new files included), and which of those lie outside its areas.
claim --area <path> ...The lane that needs the areas (or the main folder)Adds areas to the folder it is run in, with the same overlap check as new. In the main folder it creates .lane.json if there is none yet.
release --area <path> ...The lane that holds the areas (or the main folder)Gives areas back, so that another lane can claim them.
run <typecheck|test|build|e2e|server|client>A lane, or the main folderRuns the matching npm script (typecheck, test, build, test:e2e, dev:server, dev:client) with PORT set to that folder's server port and CLIENT_PORT set to its client port. You see the script's own output and get its exit code.
handin [--build] [--e2e]A lane onlyRuns the type check and the unit tests, plus the build and the browser tests when asked. Lists the files that differ from the base, marks the strays, and prints the LANE HAND-IN block. It ends with a non-zero exit code when a check failed or a stray exists.

new refuses, and changes nothing, when the lane or its branch already exists, when no area is given, when an area does not stay inside the repository, or when an area overlaps one that another lane or the main folder holds. In the last case it names who holds it.

What the tool never does: it never deletes a lane, never commits, pushes or merges, and never runs PowerShell. It handles one new at a time, so two lanes made at the same moment cannot get the same number or the same area. For a command it does not know, it prints one line of usage.

Packages. The checks need the project's packages. --install runs npm ci in the lane, so the lane has its own set. Where this was measured, that took about a quarter of a minute and a little over 200 MB of disk for each lane. Without --install, the lane uses the packages installed in the main folder, because the lane folder is inside it. That works, but a reinstall in the main folder then disturbs your checks while it runs. You can still run npm ci in the lane later.

3. Your first session, if you can run commands

If the only shell your tool has is PowerShell, you cannot run commands here (rule 6 in AGENTS.md). Use section 4 instead.
  1. Start in the main folder and change nothing there. Read AGENTS.md. Running status and new is all you do in the main folder.
  2. See what is taken. 
    npm run lane -- status
    It lists the main folder and every lane, with the areas each one holds.
  3. Choose your names. Use lower-case letters, digits and dashes only, starting with a letter or a digit, and at most 40 characters. For the provider, use the one-word name of the product you are, such as codex, cursor, gemini or grok. For the task, use one to three short words, such as tonk-bot or pool-lights. The workspace owner later commits your work with you as the author, so use a name that says plainly who you are.
  4. Choose your areas. Pick the smallest set of folders and files that covers the task, and include its tests. The code map shows what lives where.
  5. Make the lane. 
    npm run lane -- new codex tonk-bot --area server/games/tonk-bot.ts --area tests/server/tonk.test.ts --install
    If the tool refuses, it changes nothing and says why:
    It saysWhat to do
    The lane or its branch already existsChoose another task name. If it is your own lane from an earlier session, go into it and carry on.
    No area was givenAdd at least one --area.
    An area does not stay inside the repositoryWrite the path from the top of the repository with forward slashes. Do not use .., a drive letter or a leading slash.
    An area overlaps one that is already heldThe message names who holds it. Choose a narrower area, or ask the workspace owner. See section 5.
    A name or an area is not written the allowed wayNames: lower-case letters, digits and dashes. Areas: a plain path with forward slashes and no wildcards.
  6. Read what it printed, then go into the lane folder. It prints the lane folder, your two ports and the next commands, like this: 
    Created lane codex-tonk-bot.
  folder: <main folder>/_provider_worktrees/codex-tonk-bot
  branch: lane/codex-tonk-bot, started from <integration branch> at 0123456789ab
  areas:  server/games/tonk-bot.ts, tests/server/tonk.test.ts
  ports:  server 3101, client 5201
Uncommitted work in the main folder is NOT in the lane: the lane starts from the last commit on <integration branch>.
Next:
  cd "<main folder>/_provider_worktrees/codex-tonk-bot"
  npm run lane -- status
  npm run lane -- run test
  npm run lane -- handin
    With --install, npm's own lines appear in the middle, before Next:. From here on, every command and every edit happens in the lane folder. If your tool starts each command in the main folder again, begin every command with cd "<your lane folder>" &&. Your file tools need the same care: read and save files by their full path inside your lane folder. A path such as server/games/tonk-bot.ts, given from the folder you were started in, is the main folder's file. If handin does not list the files you changed, your edits went to the wrong folder: stop and tell the workspace owner. The tool works out where it is from the folder it is started in: started in the main folder, run server would use the main folder's ports.
  7. Run the checks once before you change anything. 
    npm run lane -- run typecheck
npm run lane -- run test
    They should pass. If one fails now, it is not your change. Run it once more: a test that runs out of time on a busy machine usually passes the next time. If it still fails, copy the output, tell the workspace owner, and ask whether to go on.
  8. Do the work. Edit only inside your areas. Now and then run npm run lane -- status: it shows your changed files and any that lie outside your areas. Your lane's block looks like this, and outside areas should stay at 0: 
    LANE codex-tonk-bot
  folder:        <main folder>/_provider_worktrees/codex-tonk-bot
  provider:      codex
  task:          tonk-bot
  branch:        lane/codex-tonk-bot
  areas:         server/games/tonk-bot.ts, tests/server/tonk.test.ts
  ports:         server 3101, client 5201
  changed files: 2 (compared with base 0123456789ab; uncommitted and untracked included)
  outside areas: 0
  9. See it run, if your change shows in the browser. Start two commands that keep running. Neither one returns, so give each its own terminal, or start it in the background if your tool has no terminal: 
    npm run lane -- run server
npm run lane -- run client
    Open http://localhost:<your client port>. Stop both when you are done: a server left running keeps its port busy. Then check that they are really gone, as shown under Stopping your servers.
  10. Hand in. 
    npm run lane -- handin
    Add --build or --e2e when you were asked to. Fix what it reports and run it again, until every check says PASS and there are no strays. If a check keeps failing for a reason that is not your change, do not go round again: see Troubleshooting. Paste the whole block, from the line LANE HAND-IN to the end of the output, unchanged, where you were asked to report.
  11. Stop. Do not edit the lane while it is being reviewed. A review counts only for the exact diff it looked at. If you must change something, say so, make the change, and hand in again.

Already in a lane, or coming back in a later session? If the folder you were started in is under _provider_worktrees/, it is your lane: begin at step 7. If you come back later, your lane and its files are still there: find it with npm run lane -- status, go into its folder and carry on. Do not make a second lane for the same task.

4. Your first session, if you cannot run commands

Some tools can read and write files but cannot run a command. That is fine: the workspace owner runs the commands for you.

  1. Read AGENTS.md and this page.
  2. Ask the workspace owner for a lane. Give four things: your provider name, a task name, the areas you need, and whether the task needs the browser tests. For example: 
    Please make a lane for me.
provider: gemini
task: pool-lights
areas: client/src/world/Parts.tsx, tests/client/world.test.ts
browser tests: no
  3. Wait for the answer. The workspace owner makes the lane and tells you its folder, its areas and its ports.
  4. Work in that folder only. Open, create and change files only under the lane folder, and only inside your areas. Write LF line endings.
  5. Ask for the checks. When your change is ready, ask the workspace owner to run the hand-in in your lane. You cannot run it, so do not guess its result: never write a hand-in block yourself, and never say a check passed unless you were shown its output.
  6. Fix and ask again. The workspace owner posts the block. If a check failed or a file is a stray, fix it and ask for the hand-in again.
  7. Stop when the block is clean, and wait for the review.

5. Areas, and how overlaps are refused

  • An area is a path written from the top of the repository: a folder such as client/src/world, or one file such as server/games/tonk.ts.
  • Use forward slashes, on Windows too. A backslash, a wildcard such as *, .., a leading slash and a drive letter are all refused.
  • A folder area covers everything inside it.
  • An area may name a file or folder that does not exist yet. That is how you claim room for new code.
  • Two areas overlap when they are the same, or when one is a parent folder of the other. Upper and lower case make no difference.
  • An area that overlaps one held by another lane, or by the main folder, is refused. The tool names who holds it and changes nothing.
Already heldYou ask forResult
server/gamesserver/games/tonk.tsRefused. The folder around your file is held.
server/games/tonk.tsserver/gamesRefused. Your folder would take in a file that is held.
client/src/worldClient/Src/WorldRefused. It is the same area; case makes no difference.
server/games/tonk.tsserver/games/tonk-bot.tsFine. Two different files.
client/src/uiclient/src/ui-kitFine. The names only start alike; neither folder is inside the other.

A refusal looks like this:

Refused: area "server/games/tonk.ts" overlaps "server/games", which lane cursor-card-rules holds. Choose another area, or ask the workspace owner to sort it out.

When you are refused: choose a narrower area (one file instead of its folder), or wait until the holder has finished, or ask the workspace owner. The owner can ask the holder to release the area, or can line up the two tasks one after the other.

The main folder holds areas too. The workspace owner claims areas there for work that is in flight in the main folder, so that no lane starts on top of it. In status they show under provider owner, task main.

Changing your areas later

  • Wider: ask the workspace owner first. The owner runs npm run lane -- claim --area <path> in your lane, or tells you to run it. The same overlap check applies.
  • Narrower: run npm run lane -- release --area <path> in your lane for an area you no longer need, and say so in your report. Others can then claim it.
  • Never by hand: do not edit .lane.json yourself. The tool checks areas for overlap when it writes them, and handin checks them again and fails on an overlap.

Strays

A stray is a changed file outside your areas. status lists strays, and handin fails while one exists. Either put the file back the way it was, or ask the workspace owner to widen your areas. Do not hand in with a stray and a promise to explain it.

6. Ports

FolderLane numberGame server (PORT)Client (CLIENT_PORT)
Main folder030005173
First lane131015201
Second lane231025202
Lane number nn3100 + n5200 + n
  • A new lane gets the smallest number that is free, starting at 1. Your ports are printed when the lane is made, and status shows them again.
  • Always start the app through the lane tool: npm run lane -- run server and npm run lane -- run client. The tool sets PORT and CLIENT_PORT for the script. The game server listens on PORT. The client's dev server listens on CLIENT_PORT and passes the game traffic (/socket.io) on to http://localhost:<PORT>. So your client talks to your server and to nobody else's.
  • If you type npm run dev:server or npm run dev:client yourself, neither variable is set and the script uses 3000 or 5173. Those are the main folder's ports. Do not do that in a lane.
  • Open http://localhost:<your client port> in the browser.
  • The browser tests choose a free port of their own for each run. They do not use your lane's ports, and several lanes can run them at the same time.
  • The tool wraps six scripts only. npm start (one process, after a build) reads PORT, and npm run dev:xr (the client over https for a headset) reads both variables. If you need one of them, set the variables to your lane's numbers yourself.
  • The older prototype's scripts, npm run dev and npm run preview, always use port 4173 in every folder, so only one of them can run on a machine at a time. Ask the workspace owner before you use them.

Stopping your servers

In a terminal, Ctrl+C stops the command. If you started it in the background, or your tool stopped the command for you, check that the server is really gone: on Windows, ending the shell does not end the server it started, and the server keeps the port. Do this for each of your two ports (3101 stands for your own port):

ShellSee what listens on the portStop that process
cmdnetstat -ano | findstr LISTENING | findstr :3101taskkill /PID <number> /T /F
Git Bash on Windowsnetstat -ano | grep LISTENING | grep :3101taskkill //PID <number> //T //F
A POSIX shelllsof -ti tcp:3101 -sTCP:LISTENkill <number>

The number is the last one on each line that netstat prints (the game server shows two lines with the same number), or the only thing lsof prints. If nothing is printed, nothing listens there and the port is free. Stop only a process on your own lane's ports that you started yourself. If something else holds one of your ports, do not stop it: tell the workspace owner.

8. How your work gets into the game

  1. You hand in. You paste the block where you were asked to report, and you stop editing.
  2. A different provider reviews the exact diff. That is every difference between the base commit and the files in your lane: changed, new and removed. The reviewer is never the author, and never another session of the author's provider.
  3. If the reviewer asks for changes, you make them in the same lane and hand in again. The new diff is reviewed again, because a review counts only for the diff it looked at.
  4. The workspace owner commits your lane on its branch, with you as the author.
  5. The workspace owner merges that branch into the integration branch. Now your work is in the game.
  6. The lane is finished. The workspace owner gives its areas back and removes the lane when it is no longer needed. The tool never removes a lane, and neither do you.

At no point do you commit, push, merge or rebase.

If you are asked to review a lane

  • You must be a different provider from the author.
  • Read the lane. Do not change anything in it.
  • Review exactly what the hand-in block names: that lane, that base commit, those changed files. In the lane, git diff <base commit> shows the changes to files git already knew, and git status lists the new files. Neither command changes a file.
  • Say what you checked and what you found, where you were asked to report.

9. What the workspace owner does

  • Keeps the main folder and its branch, the integration branch. Nobody else edits there.
  • Creates lanes on request, and always for a provider that cannot run commands. It tells that provider the lane folder, the areas and the ports.
  • Holds the claims for work in flight. It claims areas in the main folder for work going on there, widens a lane's areas when asked, and decides who gets an area when two tasks want the same one.
  • Runs the checks and the hand-in for providers that cannot.
  • Integrates. It makes sure a different provider has reviewed the exact diff, commits the lane with the author's name, and merges it into the integration branch.
  • Keeps lanes usable. It commits shared files so that new lanes have them, brings a lane up to date when it needs newer work, and removes lanes that are finished. After it brings a lane up to date, it sets base in that lane's .lane.json to the integration commit it brought in. Otherwise status and handin count every file that came in as a change made by that lane.
  • Decides about dependencies. Any change to the dependencies in package.json, or to package-lock.json, goes to the workspace owner first.

Ask the workspace owner when you need a lane and cannot make one, you need a wider area or one that someone else holds, a file you need is missing from your lane, a check fails for a reason that is not your change, you need a new dependency, or you are not sure a rule allows something.

10. What never to do, and why

NeverWhy
Edit, create or remove files in the main folder.Other work is in flight there. Your edit can overwrite it, and nothing would show who made it.
Edit outside your areas.Another lane may hold that file, and two versions of one file cannot both go into the game.
Commit, push, merge or rebase.Only reviewed work is committed, by the workspace owner, under the right author. A merge or rebase also changes the diff the reviewer saw.
Delete a lane or a branch.It can hold work that is not in the game yet, and the tool finds a lane by its folder and its branch.
Change the dependencies in package.json, or change package-lock.json, without asking first. To install, use npm ci, never npm install.Every lane and the main folder build from the same lock file. A change there changes everybody's build, and npm install can rewrite it without telling you.
Use port 3000 or 5173, or start a server without the lane tool.Those ports belong to the main folder. A second server on a port does not start, or a browser ends up talking to the wrong game.
Use PowerShell in any form: no powershell, no pwsh, no .ps1 file, and not through another program.It is not allowed for any agent on the machines this workspace runs on, and nothing here needs it: the tool and the checks run with Node and npm.
Save files with CRLF line endings.The repository keeps LF on every checkout, and some tests read files as text and match on the line breaks.
Put anything private in a file: a person's name, an email address, a home-folder path, a key or token, the name of a private chat channel.The repository is public. Anyone can read every file, and git history keeps a line even after it is removed.
Add art, sound, fonts or models that were not made in this project's code.The app ships only original content that its own code draws and plays, so there are no rights to clear and nothing to download.
Let the client decide a card, a turn or a score.The server deals and checks every move, so that each player sees only their own cards and nobody can cheat.
Write or change a hand-in block by hand, or say a check passed that you did not see pass.The block is the evidence for your work. A typed one proves nothing.
Edit a lane while it is being reviewed.A review counts only for the exact diff it looked at.
Edit .lane.json by hand.Areas a person writes there never went through the overlap check; handin fails when they overlap somebody else's.
Use git stash, git reset or git clean, or switch your lane to another branch.The stash is shared by every folder of the repository, and the others can throw away work or break the link between your lane and its branch.

The first eleven rows are the working rules in AGENTS.md. The last four follow from them.

How to pick sensible areas

  • Claim the code and its tests together. Tests live in their own folder tree, so they need their own --area.
  • One game is three files: its rules, its bot and its test file. Claim the ones you will change.
  • Prefer files to folders. A folder area blocks everything inside it for everybody else.
  • Some files are wanted by many tasks: shared/protocol.ts, server/rooms.ts, client/src/App.tsx, client/src/ui/actions.ts and tests/e2e/helpers.ts. Claim one only when you must, keep the change small, and release it when you are done with it.
  • Types cross areas. The client imports types from shared and from server/games, and shared/protocol.ts imports each game's view type. A change to what a game sends can break the type check in files outside your areas. Do not fix those files yourself: tell the workspace owner.

12. Troubleshooting

What you seeWhyWhat to do
In your lane, npm says Missing script: "lane", or tools/lane.mjs is not there.The lane was made from a commit that did not have the tool yet. new said so when it made the lane.From inside your lane, run the main folder's copy, as new told you: node "<main folder>/tools/lane.mjs" <command>. Do not copy the tool into your lane. Tell the workspace owner, because such a lane may lack other new files too.
You used run client, but the client starts on 5173, or says 5173 is in use.The lane was made from a commit in which the client did not read CLIENT_PORT yet, so it falls back to the main folder's ports.Stop it at once and tell the workspace owner. Do not run the client in that lane until it has been brought up to date.
A file you were told about is not in your lane.It is not committed in the main folder yet. A lane starts from the last commit; work that is not committed in the main folder is not in it.Ask the workspace owner to commit it and to bring your lane up to date. Do not copy the file over: it would count as your change.
A port is busy: the server stops with EADDRINUSE, or the client says its port is already in use.A server from an earlier run is still going, or another program has the port.If you started a server on that port earlier, it is still running: stop it as shown under Stopping your servers. If you did not start it, do not stop it: find the lane with that port in npm run lane -- status and tell the workspace owner. Do not move to another port by hand, and never to 3000 or 5173.
The browser tests stop at once and say the browser is missing.Playwright's browser has not been downloaded on this machine.Run npx playwright install chromium-headless-shell once, then run the tests again. It is once for the machine, not once for each lane.
A check cannot find a program or a package (tsc, vite, vitest, "Cannot find module").No installed packages are within reach of your lane.Run cd "<your lane folder>" && npm ci. It installs exactly what package-lock.json lists and changes neither that file nor package.json. Do not use npm install for this.
npm ci ends with warnings: a count of vulnerabilities with the advice to run npm audit fix, or a package whose install script was not run.npm prints these after every install. They do not come from your lane.Leave them alone. The checks, the build and the app work as they are. Do not run npm audit fix or approve anything: that changes package.json or package-lock.json, which everybody shares. If you think a package needs an update, tell the workspace owner.
npm ci cannot run in your lane, for example because your tool has no network.It has to download the packages.Try the checks anyway: a lane can use the packages installed in the main folder. If they cannot find their packages, ask the workspace owner to run npm ci in your lane.
A lane command says it cannot write lane.lock, or that your session may not be allowed to change the workspace.new, claim and release write a lock in the repository's shared git folder, and your tool may only be allowed to write inside your lane.Ask the workspace owner to run that command for you.
A lane command says another lane command still holds the lock.Somebody else is making a lane or changing areas at this moment.Wait a little and try again. If it stays, tell the workspace owner. Do not remove the lock file yourself.
handin reports a stray that you did not mean to change.A tool changed it. The usual ones: package-lock.json after npm install, a file your editor saved again, or a new file made in the wrong folder.Put a file git knows back with git -C "<your lane folder>" restore <path>; this throws away your change to that one file. Move a new file into your areas, or remove it. If the file really must change, ask the workspace owner to widen your areas.
A unit test you did not touch fails with Test timed out.The machine was busy, for example because other lanes were running their checks at the same moment. Some tests play whole games and need a few seconds.Run the check once more. If it fails again, hand in anyway: paste the block as it is, say under it which test ran out of time, and tell the workspace owner. Do not change a test or a time limit outside your areas.
A check prints no error of its own and ends with a very large exit code, such as 3221225477.The program itself crashed. On Windows that number means a memory fault inside the process. It is not a result of the type check or of a test.Run the check again. If it happens again, copy the output and tell the workspace owner.
A check fails before you changed anything, or fails in files outside your areas.The problem was already in the commit your lane started from, or your change to shared types reaches code outside your areas.Do not fix files outside your areas. Copy the output and tell the workspace owner.
You need work that reached the integration branch after your lane was made.A lane does not update by itself.Ask the workspace owner. Do not merge or rebase yourself.
A test that reads a file as text fails after you saved that file, or git warns about CRLF.The file was saved with CRLF line endings.Set your editor or tool to LF and save the file again.
new refuses.It says why, and it has changed nothing.See the list in section 3, step 5.
The only shell you have is PowerShell.PowerShell is not allowed here.Work as a provider that cannot run commands: section 4.
